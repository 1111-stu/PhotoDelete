# 整理状态与「待整理」口径规范

决策日期：2026-11-08
状态：**产品定稿，待落地代码**。
范围：首页周/月/年卡、待整理照片墙、整理页、垃圾桶、相册页、随机浏览、统计入口。
前提：产品未上线，直接改语义，**不写迁移兼容代码**；开发机本地数据可清空重来。

---

## 1. 一句话定稿

**全集是当前照片库；每张照片只有「待整理 / 待确认 / 已完成」三态，由保留信号派生，不由动作事件累加。已删除照片离开全集，只进统计账本。**

---

## 2. 核心原则

| # | 原则 | 说明 |
| --- | --- | --- |
| P1 | 状态跟照片走 | 周/月/年/相册只是过滤器，不是三本独立的账 |
| P2 | 三态 MECE | 每张当前库照片同一时刻只属于一个状态 |
| P3 | 信号派生 | 用「是否在垃圾桶 / 是否有保留信号」判定，不记“发生过什么” |
| P4 | 暂存不算完成 | 入垃圾桶只改变队列归属，不写完成账本 |
| P5 | 删除离开全集 | 提交删除后照片不再参与三态统计，只进统计账本 |
| P6 | 状态与账本分离 | 卡面读三态；统计入口读提交后的历史账本 |
| P7 | 一个页面一个主数字 | 其余状态只做辅助信息，禁止混算 |

---

## 3. 全集与三态

### 3.1 全集

```
U = 当前照片库里的照片
```

已删除照片 **不属于 U**，不保留任何三态；删除记录只服务统计入口。

### 3.2 三态定义

| 状态 | 文案 | 判定 | 含义 |
| --- | --- | --- | --- |
| `.pending` | 待整理 | 无保留信号，且不在垃圾桶 | 还需要用户做决定 |
| `.staged` | 待确认 | 在 `deleteCandidates` | 已倾向删除，等待提交 |
| `.completed` | 已完成 | 有保留信号 | 已有明确去向，不再占待整理 |

### 3.3 保留信号

满足任一条件即为 `.completed`：

1. **在 Poca 内**收藏了这张照片
2. **在 Poca 内**把它加入了用户相册
3. 压缩流程生成的新照片（在压缩完成时写入持久化完成集合）
4. 显式保留（预留动作，本期未实现）

**关键口径**：完成信号来自「用户在 Poca 里做了什么」，不是照片当前的外部状态。

- 系统收藏标记（`asset.isFavorite`）只是属性，不构成已完成
- 系统里本来就在某个相册，不构成已完成
- 共享相册、系统智能相册同样不参与判定

这样旧相册、旧收藏仍然留在待整理队列里，可以继续被清理。

## 4. 派生函数

```swift
enum PhotoDisposition {
    case pending    // 待整理
    case staged     // 待确认
    case completed  // 已完成
}

func disposition(for asset: PHAsset) -> PhotoDisposition {
    if deleteCandidateIDs.contains(asset.localIdentifier) {
        return .staged
    }
    if completedAssetIDs.contains(asset.localIdentifier) {
        return .completed
    }
    return .pending
}
```

要求：

- 全 App **只此一份**判定逻辑，各页面禁止自行拼接条件。
- `completedAssetIDs` 存的是「Poca 内明确保留过」的持久化集合：App 内收藏、App 内入册、压缩生成、未来的显式保留。
- 系统收藏标记、系统相册成员不参与判定；在系统相册里点收藏不会改变 Poca 进度。
- 一次性动作（收藏/入册）完成后是单向的：之后在系统里取消收藏或移出相册不会自动回退；只有整理页的撤销会回滚。
- 批量统计时先构建 `deleteCandidateIDs` / `completedAssetIDs` 两个 Set，再单次遍历照片。

### 4.1 Seen（已浏览）不是第四态

- Seen 只是 `.pending` 的子属性：待整理（没看过）/ 待整理（看过）。
- 本期不在全局状态里持久化；只在整理会话内计数，用于「本轮看过 N 张」。
- 不参与待整理、已完成、随机排除的任何计算。

## 5. 状态转移

| 起点 | 动作 | 终点 | 说明 |
| --- | --- | --- | --- |
| 待整理 | 上滑入垃圾桶 | 待确认 | **不写**完成集合 |
| 待确认 | 单张移出 / 移出所选 / 取消待删除 / 取消所有 | 待整理 | 派生自动完成，无回滚代码 |
| 待确认 | 确认删除 | 离开全集 | 写入统计账本；卡面分母缩小 |
| 待整理 | 在 Poca 内收藏 | 已完成 | 写入持久化完成集合 |
| 待整理 | 在 Poca 内加入用户相册 | 已完成 | 写入持久化完成集合 |
| 待整理 | 压缩生成新照片 | 已完成 | 新照片写入持久化完成集合 |
| 已完成 | 系统里取消收藏 / 移出相册 | 仍为已完成 | 已完成是单向的；只有整理页撤销才回滚 |
| 已完成 | 整理页撤销刚才的收藏 / 入册 | 按撤销前状态恢复 | 依赖 actionHistory 的 `wasReviewed` |

## 6. 各页面口径

| 页面 | 主数字 | 辅助信息 | 禁止 |
| --- | --- | --- | --- |
| 首页周/月/年卡 | `pending` 数量 | 仅照片总数与体积 | 不显示 `staged`、完成百分比；不用 `pending + staged` 冒充一个数 |
| 待整理照片墙 | 每天/每月的 `pending` | 无 | 只铺 `pending`；已完成/垃圾桶不出现在墙上 |
| 相册「整理」入口 | `pending` 数量 | 本轮待删 / 本轮保留 | 旧相册照片按 pending 继续清理 |
| 相册浏览 / 收藏分类 | 原来源全部照片 | 位置计数 | 不当作待整理队列，不承诺待整理分母 |
| 整理页顶栏 | 本轮序号 / **待整理总数** | 本轮待删 / 本轮保留 | 不把已完成、待确认算进本轮总数；相册浏览、收藏分类保持原来源 |
| 垃圾桶 | `staged` 数量 | 预计释放空间 | 不把垃圾桶内容算已完成 |
| 相册页 | `pending` 数量 | 三段式：已完成 / 待确认 / 待整理 | 不用会随分母缩小的百分比做主展示 |
| 随机浏览 | 只从 `pending` 抽取 | — | 不抽 `staged` / `completed` |
| 统计入口 | 累计删除、累计释放 | 当前三态快照 | 不把状态数当释放量；不混算 |

### 6.1 首页周期卡示例

```
本周 · 120 项 · 3.2 GB
待整理 6
```

- 入桶 3 张：待整理 9 → 6，待确认 0 → 3。
- 移出 3 张：待整理 6 → 9，待确认 3 → 0。
- 确认删除 3 张：照片离开全集，本周变为 117 项，待整理仍为 6，待确认 0。
- **分母缩小是预期行为**，不回填“已完成 3”。

## 7. 统计入口与账本

### 7.1 分工

| 系统 | 数据 | 驱动 |
| --- | --- | --- |
| 三态 | 当前库照片的 `pending / staged / completed` | 首页、相册、照片墙、随机浏览 |
| 账本 | 已提交删除、压缩节省、时间戳 | 统计入口、成就、连续天数 |

### 7.2 账本记录

- 删除：沿用 `CleanupStatsStore` 会话记录（日期、删除数、估算释放空间）。
- 压缩：沿用 `ImageCompressionHistoryStore` / `VideoCompressionHistoryStore`；以 `originalDeletedAt` 对账，避免“压缩省一次、删原图再省一次”。
- 收藏 / 入册：本期不作为释放空间入账；如统计入口需要“整理动作数”，再单独增加事件类型。
- 时间线按**清理发生日期**聚合，不按照片拍摄日期；因此不需要为已删除照片保留 tombstone。

### 7.3 统计入口信息架构（本期）

1. **当前状态**：待整理 / 待确认 / 已完成（当前库快照）
2. **累计成果**：累计删除张数、累计释放空间
3. **历史**：按月聚合的删除与释放（复用 `CleanupMonthlySummary`）
4. **待确认**：垃圾桶数量与预计释放

## 9. 交互与文案规则

1. 状态词固定：**待整理 / 待确认 / 已完成**。
2. 「已整理」只用于完成态；删除后的历史统一叫「累计删除」，不叫「已整理」。
3. 提交删除是唯一单向门；按钮写「确认删除」，并展示预计释放。
4. 库状态用计数；百分比只用于本轮会话等分母固定的场景。
5. 垃圾桶从「待确认」到「离开全集」要有一致的成功反馈（数量 + 预计释放）。
6. 不解释“为什么数字变小”；删除即离开全集，是产品语义。

---

## 10. 边界情况与待确认项

| 情况 | 规则 |
| --- | --- |
| 老收藏 | 不算已完成；仍在待整理里，等待在 Poca 内处理 |
| 老相册 | 不算已完成；相册「整理」入口按 pending 继续清理 |
| 共享相册 / 系统智能相册 | 不参与判定 |
| 在系统里取消收藏 / 移出相册 | 不影响 Poca 状态；完成是单向的 |
| 整理页撤销收藏 / 入册 | 按撤销前的 `wasReviewed` 恢复 |
| 压缩生成的新照片 | 自动算已完成，避免重新排队 |
| 压缩历史被清空 | 完成集合独立持久化，不受影响 |
| 新拍照片 | 立即进入待整理 |
| 外部 App 删除照片 | 照片离开全集；不记账 |

## 11. 单测清单

1. 入垃圾桶后，`disposition == .staged`，`completedAssetIDs` 不新增。
2. 从垃圾桶单张移出 / 移出所选 / 取消全部后，回到 `.pending`。
3. Poca 内收藏 → `.completed`；系统收藏标记本身不算完成。
4. Poca 内加入相册 → `.completed`；系统里本来就在相册不算完成。
5. 撤销收藏 / 入册后按 `wasReviewed` 恢复；后续在系统里取消收藏/移出相册不回退。
6. 压缩生成的新照片 → `.completed`；清空压缩历史后仍为 `.completed`。
7. 周期统计：`pending` 不含 `staged`、不含 `completed`。
8. 随机浏览排除 `staged ∪ completed`。
9. 提交删除后照片离开全集，账本新增一次删除记录。
10. 取消所有操作后，候选照片全部回到 `.pending`。
11. 新拍照片默认 `.pending`。
12. 统计入口当前状态与累计账本分开计算，不互相污染。
