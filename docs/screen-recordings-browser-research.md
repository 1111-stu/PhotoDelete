# 屏幕录制专项：复用调研与信息原型 v1

日期：2026-10-09。依据当前 `ios-app/` 工作区（包含现有暂存改动）与用户提供的两张参考截图。此次产出是调研和可交互原型，没有修改原生 App。

## 结论

录屏识别、资产集合、缩略图、视频播放、整理状态持久化、候选库及批量确认都已存在。新增工作集中在一个专项网格页面、一套四维筛选状态，以及网格到整理会话的范围传递。现有完整页面不宜原样搬用：相册浏览缺录屏元信息和整理状态，高级清理列表是纵向多选列表。

## 必须补齐的逻辑

1. 时间条件：全部 / 15 天以前 / 30 天以前 / 180 天以前 / 1 年以前。使用创建日期和 Calendar 计算边界；“1 年”按自然年回退，不硬编码 365 天。按当前时区的当天零点计算，严格早于对应日期；无日期资产仅在“全部”中出现。
2. 状态条件：全部 / 待整理 / 已整理。建议采用 `DataManager.isReviewed` 所代表的“在本 App 中已做过整理动作”；已进入候选库也算已整理，卡片可额外显示待删除状态。系统收藏本身不等于在本 App 整理过。实现前统一查询 policy，避免与首页周期统计已有的“收藏也算已整理”逻辑混淆。
3. 当前容量不能冒充可释放容量。全已知时显示真实总大小；未完成读取时显示“计算中”；存在未知/iCloud 时显示已知容量和未知项数。现有首页以及 `getPhotosForAdvancedCleanup(.screenRecordings)` 使用时长与分辨率估算，不能直接当作真实文件大小。
4. 排序：真实大小降序 / 最近在前 / 最早在前。同大小按创建日期，再按 assetID，避免抖动；缺失日期统一放末尾；未知大小位于可靠大小后，不能当作 0 MB。
5. 分组与排序：不分组时全列表排序；日/月分组时先按时间桶分组，再对组内排序。最近、大小排序的组顺序为最近在前；最早排序则组顺序最早在前。sheet 在分组+大小组合下显示一句“分组内按占用排序”。
6. 当前高级列表只读取可见范围大小并不断重排，不能直接承诺整个录屏库严格按真实大小排序。新页面需要后台分批获取全部录屏的大小元数据；先展示缓存与未知状态，批次就绪时更新，避免用户正在点击时卡片移位。
7. 会话传递：`SwipePhotoView` 当前没有显式资产范围参数；`PhotoReviewSource` 对 `.screenRecordings` 类别仍应用全局日期排序。需要传递此次筛选的 assetIDs、明确顺序和独立范围标识，防止开始整理后丢失筛选或覆盖其他范围进度。整理开始时固定本轮范围，照片库变化仅剔除已不存在资产；返回网格后刷新。

## 页面 1：屏幕录制网格

从专项入口系统 push 进入，使用系统返回按钮和原生侧滑返回。当前提案采用“浏览 → 开始整理”的主流程，多选删除为备选方向，未在第一版混入双重主操作。

| 区域 | 展示内容 | 行为 |
| --- | --- | --- |
| 导航栏 | 返回、屏幕录制、筛选与排序图标 | 右侧打开系统 sheet；非默认条件有小标记和可访问性提示 |
| 汇总区 | 当前结果录屏总大小、共 N 项、待整理 M 项 | 随筛选同步变化；总大小包含已整理资产，不代表可释放容量 |
| 条件提示 | 非默认的时间/状态/分组/排序摘要 | 默认不堆放额外提示；无结果时可清除筛选 |
| 三列网格 | 1:1 预览、中央播放图标、右下时长 | 点击仅预览；网格不自动播放；正方形裁切不代表视频实际比例 |
| 卡片元信息 | 日期左侧、容量右侧，同一行；左上已整理标记 | 独立深灰卡片包住预览和元信息；三列使用 `25.11.02` 短年份，完整日期留在预览和无障碍标签；未知容量显示 iCloud，详情注明大小未知；窄屏采用两列 |
| 分组标题 | 日期或月份、组内项数 | 仅选择日/月分组时出现；无日期单独在末尾 |
| 底部主按钮 | 开始整理 · M 项 | 仅整理当前筛选结果中的未 reviewed 资产，顺序跟随浏览器；不立即删除 |
| 底部无待整理状态 | 暂无待整理内容（禁用） | 已整理录屏仍可预览；不是无录屏空页 |

预览使用完整视频比例；关闭后保留网格位置与筛选。网络取回 iCloud 内容沿用现有播放服务。浏览和播放都不计入整理历史。

## 页面 2：筛选与排序 sheet

使用系统 sheet，有拖动柄、标题“筛选与排序”、重置、完成。内容单选；点击即时生效，完成或下拉关闭都保留选择，不设一套未提交草稿。默认约 70% 高度，允许扩展大尺寸；小屏和大字号内容可滚动。HTML 仅表达结构，原生实现使用系统导航与 sheet。

| 分区 | 选项 | 默认 |
| --- | --- | --- |
| 拍摄时间 | 全部 / 15 天以前 / 30 天以前 / 180 天以前 / 1 年以前 | 全部 |
| 整理状态 | 全部 / 待整理 / 已整理 | 全部 |
| 时间分组 | 不分组 / 按日 / 按月 | 不分组 |
| 排序依据 | 占用从大到小 / 最近在前 / 最早在前 | 占用从大到小 |

选中项使用琥珀描边和勾选标记，未选中使用中性面。保留参考图的信息结构，使用项目 style.md 的底色、行动色、间距和圆角；不复制参考图的手写下划线和背景装饰。第一版条件只保留当前页面生命周期，重新进入恢复默认，不改变全局滑动排序设置。

## 状态矩阵

- 有录屏且有待整理：网格正常，底部可开始。
- 有录屏但均已整理：保留网格与容量，底部“暂无待整理内容”。
- 无录屏：“暂无屏幕录制”，区别于筛选无结果。
- 筛选无结果：“没有符合条件的录屏”与“清除筛选”。
- 加载中：网格形状占位；容量读取与缩略图读取独立，不阻塞整页。
- iCloud/未知大小：容量“已知 X”与未知项数；卡片显示状态，列表不自动下载原视频。
- 权限不足：沿用现有权限组件；limited 状态表示“可访问的录屏”，不宣称完整图库数量。
- 整理或系统图库变更后：刷新资产、大小缓存和 reviewed 状态，保留筛选；已删除资产不残留卡片。

## 原型与下一阶段

`designs/screen-recordings-prototype.html` 为独立可交互信息原型，使用合成示例数据与示意缩略图。支持四维筛选、容量和项数联动、分组、reset、空状态及预览结构，不访问真实 Photos、不播放真实视频，也不执行删除。模拟日期固定为 2026-10-09，使时间筛选结果可复查。

原生实现建议新增 `ScreenRecordingsBrowserView` 和四维查询状态，将既有大小查询/状态策略及必要预览组件提取共享，并为本轮整理增加显式范围。验证重点为时间边界、缺失日期、状态一致性、分组排序、未知大小、筛选到会话范围传递、回到网格后的增量更新。此阶段未运行 iOS 构建或 Photos 真机验证。

验证记录：通过 Node VM 与轻量 DOM 桩执行原型脚本，检查语法、唯一元素 ID、19 项/14 项待整理初始统计、1 年以前筛选、状态组合空结果、重置、月份分组与最早排序、按当前顺序进入整理队列、保留后状态更新、全部已整理/暂无录屏/iCloud 五项未知容量状态。该检查不等于原生移动端或无障碍验收。

后续截图已通过本机独立 Chrome 配置与 Playwright 生成。用户要求每条视频使用完整卡片、日期容量同一行后，原型更新为 v2：卡片圆角 16、封面圆角 10、内边距 6、列间距 8、行间距 10；日期和容量字号均为 11，并使用短年份。手机容器宽度不超过 379 时变两列。已通过 320、360、375、390、414 与 1320 页面宽度下的真实浏览器检查：日期和容量同一行、无重叠、封面正方形、页面无横向溢出；已整理筛选和 iCloud 未知容量状态通过。截图为 `designs/screen-recordings-cards-v2.png` 与 `designs/screen-recordings-filter-v2.png`。
